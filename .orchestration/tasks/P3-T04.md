## 2. Objective

Generalize the data guard's SQL validation from "exactly the known fixed metric query" to a structural aggregate-only validator over the SQLGlot AST, so new metric queries can be added safely without weakening governance. Runtime behavior of the existing workflow stays unchanged.

## 3. Defensive engineering scope

## 4. Background / fixed decisions

- Current: scripts/data_guard.py validates single-SELECT + rejects mutation/multi-statement/PII columns, and executes a fixed aggregate query.
- **Decision 1 — structural aggregate-only rule** (`validate_sql` generalization): a query is acceptable iff ALL hold:
  1. exactly one statement, expression type SELECT (no UNION/INTERSECT/EXCEPT);
  2. every projection is an aggregate function call (COUNT/SUM/AVG/MIN/MAX) or a plain column that appears in GROUP BY;
  3. `SELECT *` denied;
  4. FROM references only tables in an allowlist (module-level constant seeded with the existing demo table);
  5. PII columns (existing list, extended by P3-T03 entities where sensible) denied in EVERY clause — projection, WHERE, GROUP BY, HAVING, ORDER BY, and inside any subquery;
  6. subqueries are allowed only if they themselves satisfy rules 2-5; CTEs same;
  7. DML/DDL/engine-control statements remain denied (existing behavior).
- **Decision 2 — contract preserved**: the TS dataProxy/metric_query path and E2E artifacts stay unchanged (existing named query must pass the new validator). No TS changes.
- **Decision 3 — result booleans extended**: the guard's returned evidence booleans gain the new rejection classes (e.g. non_aggregate_projection_rejected, table_not_allowlisted_rejected) following the existing pattern.
- Tests: acceptance (multi-column GROUP BY aggregate over allowlisted table) + rejections (bare column projection; SELECT \*; PII in WHERE; PII inside subquery; UNION; unknown table; HAVING with PII). Coverage >= 85%.
- `.agents/worklog/**` allowed for your process records.
