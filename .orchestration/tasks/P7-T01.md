# P7-T01: Native Hermes Skill Subset — trigger-driven skill lifecycle (no Hermes runtime)

- Author: orchestrator-fable5, 2026-07-07
- Basis: user directive "hermes-agent を呼び出さず、同等の機能を pi+flue に実装するべき"; scope bounded by `.orchestration/skills/hermes_subset_policy.md` (取り込む要素のみ).

## 1. Objective

Implement the Hermes Skill Subset natively in this repository: a trigger-driven skill lifecycle engine that automates observe → decide → apply for skill candidates, generalizing beyond the remediator-only `scripts/skill-cycle.mjs`. No Hermes Agents runtime, no new LLM calls, no new PII engine (reuse `scripts/data_guard.py` patterns / existing redaction assets).

## 2. Current state (verified)

- `scripts/skill-cycle.mjs`: remediator-specific improve-loop only (held-out eval, verdict, promotionAllowed=false).
- AutoSkill (pinned external container, `run_autoskill.sh`): candidate generation dry-run only; keep as-is per ADOPTION_PLAN principle 1 (do not reimplement, do not require it for this task).
- Registry states + TRIAGE.md + `check-skill-registry.mjs` gate: exist; promoted skills require provenance frontmatter (see `promoted/agmsg-task-protocol/SKILL.md`).
- Missing (the gap this task closes): trigger-driven create/patch/merge/discard decision flow, run-log automation, activation-hint based skill discovery (progressive disclosure).

## 3. Deliverables

1. `scripts/skill-lifecycle.mjs` with subcommands:
   - `observe --trigger task-completion|error-recovery|user-correction --task <id>`: collect evidence from `.orchestration/{reports,validation,acceptance}/<id>*`, redact via existing data_guard patterns, write `.orchestration/autoskill/inputs/<id>.manifest.json` (INPUT_CONTRACT.md compatible).
   - `decide --task <id>`: deterministic overlap analysis against ALL registry skills (candidates+promoted; match triggers/activation hints/scope) → recommendation create|patch|merge|discard + rationale → run log `.orchestration/autoskill/runs/<id>.lifecycle.md` (decision, decided_by, redaction_passed, promotion_allowed=false). Final authority stays with the calling agent/orchestrator; the engine only recommends.
   - `apply --task <id> --decision create|patch|merge|discard`: create → `.orchestration/skills/candidates/<id>.SKILL.md` with the full provenance frontmatter required by the skill_registry gate; patch/merge → improve / merge_required record; discard → run log only. Always append the corresponding triage worksheet row (TRIAGE.md record format).
2. `scripts/skill-activate.mjs`: progressive disclosure loader — rank promoted skills by activation trigger match for a `--query "<task text>"`; level 1 prints name+description, `--full <name>` prints the body.
3. `package.json` npm scripts: `skill:lifecycle`, `skill:activate`.
4. Tests: `node --test` unit tests for both scripts (fixture-based, no network); wire into the existing test entry if one exists, otherwise standalone `npm run test:skill-lifecycle`.
5. Docs: short usage section appended to `.orchestration/skills/TRIAGE.md` (how automation feeds triage) and a cross-reference line in `ADOPTION_PLAN.md`.
