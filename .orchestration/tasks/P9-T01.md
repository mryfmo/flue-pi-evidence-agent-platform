# P9-T01: 製品運用レベル到達度の全面監査(gap 抽出、report-only)

## 目的

ユーザー判定: 現状の flue_pi_ai_agent は「実際に運用できるレベル」の仕様・ドキュメント・実装コード・検証コードになっていない。製品レベルに到達するために必要な箇所を**すべて**抽出する。修正はしない(本タスクは監査・報告専用)。

## スコープ(4 面)

1. **仕様**: docs/ 配下の \*\_SPEC.md, SPECIFICATION.md, PRODUCT_REQUIREMENTS.md, FUNCTIONAL/NON_FUNCTIONAL_REQUIREMENTS.md ほか。曖昧・未定義・相互矛盾・実装と乖離している箇所。とくに初期スタブのまま薄い仕様(ABUSE_CASES 495B, AGENT_LOOP_SPEC 670B, EVIDENCE_GRAPH_SPEC 465B, HYPOTHESIS_LEDGER_SPEC 497B, THREAT_MODEL 810B, TOOL_REGISTRY_SPEC 372B 等)が製品仕様として十分かを判定。
2. **ドキュメント**: 運用者が読んで実際に運用できるか(DEPLOYMENT, OPERATIONS, RUNBOOK, SLO, SECRETS_MANAGEMENT, FAILURE_MODE_MATRIX, LITELLM_PROXY 等)。手順の再現性、前提の明記、実環境(darwin ローカル / linux CI / 本番)ごとの差分の明記。
3. **実装コード**: src/ 全ファイル + scripts/。製品品質の欠落 — エラーハンドリング、入力検証、リトライ/タイムアウト、ログ/監査の網羅、ハードコード値、モック/スタブ実装のまま本番経路に残っているもの、TODO/FIXME、未実装の宣言済み機能。
4. **検証コード**: tests/(unit/contract/security/integration/component/system/failure/regression/e2e)。カバレッジの空白、モック迂回で「通過」を装っている検証、実環境でしか検証できないのに runbook 化されていないもの、ゲート(validate-release 23 個)が実際に何を保証していないか。

## 必須の突合

- 既存分析と重複させない: `.orchestration/analysis/gap_analysis_v1.md`, `final_release_judgment.md`, `litellm_claude_code_integration_review.md`, `phase8_consistency_audit.md`, `risk_register.md` を先に読み、各 gap に「既知(参照先)/新規」を明記。
- 既知の未了事項は必ず含めて現状を再確認: LiteLLM Proxy 実起動、仮想キー実発行、ライブ LLM smoke、AutoSkill 2 周目、OpenSandbox remediation 本番接続、skill merge 3 件、P2-T07b。
- 主張には証跡: file:line、または実行したコマンドと出力(検証系の主張は実行して確かめる。例: validate-release、npm test 系)。

## 成果物フォーマット(report)

gap ごとに: `GAP-<連番> | 面(仕様/docs/実装/検証) | 重大度 P0(運用不能)/P1(運用リスク)/P2(品質) | 対象(file:line) | 現状 | 製品レベルに必要な状態 | 既知/新規 | 推定工数(S/M/L)`。冒頭にサマリ(面別・重大度別の件数、P0 の一覧)。最後に「製品到達までの推奨タスク分割案」(フェーズ順、依存関係付き)。
