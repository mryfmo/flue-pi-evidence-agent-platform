# P8-T09: PR #1 の CI 失敗と Codex bot P1 レビュー 3 件の是正

- Author: orchestrator-fable5, 2026-07-09
- Basis: PR #1(phase8-litellm-claude-code-integration)の CI 結果と bot レビュー全文。CI: Container validate 失敗(他 2 ジョブ green)。レビュー: chatgpt-codex-connector の P1 × 3。

## 1. Objective

CI の Container validate を green にし、Codex bot の P1 指摘 3 件を fail-closed 原則を保ったまま是正する。

## 2. Deliverables

1. **CI-1: コンテナに sqlite3 が無い** — 失敗原因は `tests/unit/orchestrator_fail_closed.test.ts` の `createMessagesDb` が `spawnSync('sqlite3',…)` を使うが `node:22-bookworm` に sqlite3 CLI が無く status=null(ENOENT)。platform-health 本体も sqlite3 CLI に依存するランタイム要件のため、**`Dockerfile` の apt-get install に `sqlite3` を追加**(1 語)。テスト側は変更しない。
2. **C-1: リダイレクト直後のパスがガードを素通り**(pretooluse-guard.mjs:39 指摘) — トークン開始条件が `^|\s` のみのため `printf x >policy/routing.json` や `cat <policy/routing.json` でパスが抽出されない。トークン開始を `(?:^|[\s<>|;&])` 相当に拡張(引用トークンも同様)。テスト追加: `>policy/routing.json` 形式 deny、`<policy/routing.json` 形式 deny。
3. **C-2: 統制リソースの委譲コマンド自体が拒否される**(pretooluse-guard.mjs:43 指摘) — `node scripts/orchestrator/delegate.mjs --task-id X --task-file Y --to Z --lease policy/routing.json` が `controlled_path` で deny され、CLAUDE.md が要求する統制ゾーンの唯一の正規経路が塞がる。**限定カーブアウト**を実装: コマンド全体が単一の delegate 呼び出し(先頭が `node scripts/orchestrator/delegate.mjs`、かつ `;` `&&` `||` `|` の連結・リダイレクトを含まない)である場合に限り、`--lease` と `--task-file` の**値として現れるトークン**をファイル操作パスとして扱わない。それ以外の位置に統制パスが現れたら従来どおり deny。cc_guard.rego との整合: 抽出段階(mjs)での除外とし rego は不変更でよいが、除外理由を deny 判定入力に含めない設計とすること。テスト追加: (a) delegate+--lease policy/... allow、(b) `node scripts/orchestrator/delegate.mjs --lease policy/x && rm policy/y` deny、(c) `rm --lease policy/x` deny(先頭が delegate でない)、(d) リダイレクト付き delegate deny。
4. **C-3: platform_audit_forwarder 未実装**(config.yaml:22 指摘) — LiteLLM のカスタム callback は「config 隣接の python モジュール + インスタンス」形式(例 `custom_callbacks.proxy_handler_instance`)で解決される。**`config/litellm/platform_audit_forwarder.py` を新規実装**:
   - `litellm.integrations.custom_logger.CustomLogger` 継承(import は遅延/ガード付きにして litellm 未導入環境の python ゲートを壊さない — 例: モジュール読み込み時に litellm import が失敗したらフォールバック基底クラスで型だけ満たす)。
   - success/failure イベントで **メタデータのみ**(model, input/output/total tokens, cost, latency, ステータス, metadata 内の task_id/agent_profile/tenant/data_class)を JSONL 1 行として `LITELLM_AUDIT_FORWARD_PATH`(env、未設定時は `artifacts/audit/llm_gateway_events.jsonl`)へ追記。**messages/prompt/response 本文・キー文字列は書かない**(redaction 境界の維持)。
   - `config.yaml` の callback 参照を LiteLLM 解決形式(`platform_audit_forwarder.platform_audit_forwarder`、モジュール内に同名インスタンスを定義)へ更新。
   - `scripts/check-litellm-config.mjs` に追加検査: callback 指定があれば `config/litellm/<module>.py` が実在し、かつファイル内に `messages` 本文をログする明白なパターンが無いこと(決定論の静的検査で可)。
   - pytest(tests_py/)にユニットテスト: イベント dict を与えて JSONL 出力がメタデータのみ(本文キー不在)になること、変な入力(metadata 欠落)でも例外を出さないこと。python ゲート(compile/ruff/mypy/bandit/tests cov)を全て通す。
   - `docs/LITELLM_PROXY.md` を更新: callback は実装済み、起動前提の記述を「実装済みモジュールが config 隣接に存在」へ書き換え、metadata-only 契約とログ先 env を記載。
5. **検証**: `npm run validate-release` exit 0(23 ゲート)。ローカルで `bash scripts/container-validate.sh` が実行可能な環境(docker/Apple container)なら実行し container 内テスト green を確認、不可なら報告書にその旨と根拠(Dockerfile 差分で ENOENT が解消する論拠)を記載。
