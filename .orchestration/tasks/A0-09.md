## 5. Mandatory request contract

1. Expose the remediation HTTP operation through `src/app.ts`; a schema without runtime enforcement is a failure.
2. Require a valid `Content-Type` whose media-type essence is `application/json`. Reject missing, duplicate/ambiguous, malformed, or other media types with the documented A0-06 error envelope and HTTP `415`. Do not parse or log the body first.
3. Reject a declared or actual raw request body greater than 65,536 bytes with HTTP `413`. Enforce the actual byte count before UTF-8 decoding or JSON parsing; `Content-Length` is only an early rejection hint and never proof of the actual size.
4. Decode bytes as strict UTF-8; replacement-character decoding is forbidden. Parse exactly one JSON value and require a non-null, non-array object.
5. Define schema version integer `1`. The exact closed body is `{version, workspace, issue?}`: `version` is required and exactly `1`; `workspace` is a required string of 1..4,096 Unicode code points; `issue` is an optional string of 0..8,192 Unicode code points. Reject ill-formed surrogate content, coercion, defaults, non-integers, every unknown field, and body identity/provenance fields.
6. The runtime and `schemas/remediation-request.schema.json` must enforce the same closed contract. The schema uses draft 2020-12 or the repository canonical draft, exact required fields, `additionalProperties: false`, and no coercive/default security behavior.
7. Obtain verified identity only from the A0-02 trusted request context. It must be a complete verified identity tuple and must not be synthesized from request body user/tenant/roles. Missing/unverified/malformed identity returns the canonical versioned error envelope and a documented `401`/`403` without invoking the workflow.
8. Reject every content-type, length, UTF-8, JSON, schema, version, or identity failure before filesystem access, gateway/OPA calls, workflow execution, sandbox creation, audit emission, ledger mutation, or other side effects. Rejected request bodies and sensitive identity values must not be logged.
9. A valid request reaches the remediation workflow exactly once with the validated body plus trusted identity. Do not duplicate parsing or validation downstream.
10. All failures use the existing A0-06 closed versioned error envelope (`version`, `error.code`, `error.message`, `error.request_id` as established by the repository contract), contain no stack trace/internal path/body echo, and use stable documented status/code mappings. Preserve successful response behavior.

JSON Schema `minLength`/`maxLength` is interpreted as Unicode code-point length; raw body size is separately enforced in bytes. Add astral-character boundary tests so UTF-16 code-unit counting cannot silently diverge.

## 6. Adversarial acceptance

- Missing/wrong/malformed/ambiguous content type => `415`, no body parse or side effects.
- `Content-Length > 65536`, actual 65,537-byte body, or a body whose header understates its bytes => `413`, no side effects. Exactly 65,536 raw bytes proceeds to the next validation stage.
- Invalid UTF-8, empty body, truncated/multiple/malformed JSON, null/array/scalar, unknown field, missing/version type mismatch/version other than 1, workspace/issue wrong type, length below/above boundary, lone surrogate, and coercible-looking values => documented `4xx`, no side effects.
- Body keys such as `user`, `tenant`, `roles`, `identity`, or nested authority/provenance are unknown fields and cannot replace trusted identity.
- Missing, unverified, wrong issuer/audience/verifier, anonymous, or malformed trusted identity => deny before workflow/OPA/audit/ledger/sandbox.
- A valid body with valid trusted identity invokes the workflow exactly once and passes the trusted tuple unchanged.
- Every rejection returns the closed error shape; response and captured logs contain no stack, rejected body, or secrets.
- Prove absence of side effects with spies/counters over every reachable boundary, not merely absence of final files.

## 10. Revision 2 — encoded raw-route bypass

Revision 1 is rejected. Independent cold review reproduced a critical bypass:

- `POST /workflows/%2572emediate` passes the one-pass `decodeURIComponent` guard and reaches the mounted raw Flue remediation handler. In a configured runtime this lets a caller supply `RemediationInvocation.request/trusted` directly and bypass the versioned body, identity, byte, UTF-8, schema, and side-effect boundary.
- `/workflows%2Fremediate` and `/workflows//remediate` return a non-canonical plain 404 rather than the required closed error envelope.

Required correction:

- Do not mount `flueApp` on the public Hono app. Keep it reachable only inside the private default `invokeRemediation` closure, or provide an equivalently unbypassable architecture that does not rely on a finite number of URL-decode passes or caller-controlled internal headers.
- Configure the public app's not-found response to use the canonical version-1 `404 not_found` envelope.
- Add negative tests for `/workflows/%2572emediate`, `/workflows%2Fremediate`, `/workflows//remediate`, exact, trailing-slash, suffix, and encoded variants. Every case must return the canonical envelope and leave workflow/downstream invocation at zero.
- Prove the valid `/v1/remediations` path still dispatches exactly once through the private Flue app when using the default dependency, without exposing that private route publicly.
