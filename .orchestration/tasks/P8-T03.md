# P8-T03: 基盤 Gateway → LiteLLM 接続(prod provider path + 相関 ID 伝搬)

- Author: orchestrator-fable5, 2026-07-08
- Basis: `.orchestration/analysis/litellm_claude_code_integration_review.md` 問題 1, 7, 8, 10, 16, 17(コード面)、§3.2。前提: P8-T01(INTEGRATION_BOUNDARY.md)、P8-T02(config/litellm/config.yaml, docs/LITELLM_PROXY.md)accepted。

## 1. Objective

Pi provider path の本番実装を「基盤 Gateway → LiteLLM Proxy(openai_compatible)」として接続し、(a) 承認外プロバイダへの fallback を排除、(b) PI_PROVIDER=local/prod の二系統分離、(c) task_id 等の相関メタデータ伝搬、(d) fail-closed(成功偽装なし)をコードとテストで確立する。実 LLM への接続は行わない(テストは決定論・オフライン)。

## 2. Deliverables

1. **`policy/routing.prod.json`(新規)** — 本番ルーティングポリシー:
   - providers: `litellm`(type=openai_compatible, base_url_env=LITELLM_BASE_URL, api_key_env=LITELLM_VIRTUAL_KEY)と `local` のみ。**openai / vllm / anthropic 直参照を含めない**(キー隔離: Gateway は仮想キーのみ保持、問題 9)。
   - routes: 統制タスク種別を litellm のエイリアス(`worker-fast`/`worker-main`/`worker-heavy`)へマップ。INTEGRATION_BOUNDARY.md のデータ分類マトリクスに整合(restricted は外部送信不可 → litellm route を定義しない/OPA deny に落とす)。
   - fallback chain は litellm エイリアス内のみ。**`mode=deterministic-fallback` の local を本番チェーンに入れない**(全承認モデル不達時は成功偽装せず失敗を返す。問題 7/16)。
2. **既存 `policy/routing.json` の修正(最小)** — defaults の openai エントリを除去し、承認リスト外プロバイダ参照をなくす(決定論 local スタブは維持。CI・回帰テスト用の local 系統)。`policy/routing.rego` の許可判定が新旧両ポリシーで機能することを確認(必要なら providers 許可リストを rego 側でも承認制に強化 — additive のみ)。
3. **`src/lib/productionGateway.ts` の拡張**:
   - ポリシー解決: `request.routing_policy_path` 未指定時、`PI_PROVIDER=prod` なら `policy/routing.prod.json`、それ以外は `policy/routing.json`(問題 8 の二系統分離)。
   - `ProductionGatewayRequest` に optional `task_id`・`agent_profile` を追加し、openai_compatible dispatch のリクエスト body に `metadata: {task_id, agent_profile, tenant, data_class}` を付与(§3.2 の extra_body 規約)。
   - 監査イベント(llm_gateway_call)と OTel span に `task_id`・`agent_profile` を追加(問題 17: task_id を全層の相関キーに)。
   - 失敗時の reason を機械可読に整理: 全 fallback 不達は `llm_unavailable`(問題 16 の blocked_reason に対応)、認可拒否は従来どおり理由列挙。**タイムアウト・不達を成功扱いにしない**こと。
   - 応答に LiteLLM のコストヘッダ/usage があれば `estimated_cost` に反映(なければ 0 のまま。問題 10 の記録面)。
4. **テスト**(決定論・オフライン。既存 `tests/contract/llm_contract.test.ts` のスタイルに従いローカル HTTP スタブで検証):
   - PI_PROVIDER=prod で routing.prod.json が選ばれ、litellm provider へ metadata 付きで dispatch される。
   - 全 fallback 不達で `ok:false, reason=llm_unavailable`(成功偽装なし)。
   - PI_PROVIDER 未設定/local で従来の決定論経路が不変(回帰)。
   - routing.prod.json に承認外プロバイダ参照がないことの静的検査(既存 llm_contract か新規ユニットに追加)。
5. **`docs/PRODUCTION_GATEWAY_DESIGN.md` へ追記(節 1 つ)** — 「prod provider path = Gateway→LiteLLM」の責務分割(redaction・分類・fail-closed・監査一次記録=Gateway/エイリアス解決・fallback・レート・コスト=LiteLLM。同一機能を両方で有効化しない。問題 1)と PI_PROVIDER 二系統。
