## Acceptance blocker

`FR-001` currently states: “Accept a remediation payload with workspace, user, tenant, and issue.” This makes `user` and `tenant` caller-body fields.

That text directly contradicts the already accepted contracts:

- `SPEC-04`: identity and request contexts are gateway/PEP-owned and body identity fields are rejected.
- `SPEC-15`: the runtime boundary accepts a closed version-1 request and obtains verified identity from the gateway before side effects.
- `REQ-HTTP-REQUEST-001`: the JSON body contains required `version`/`workspace`, optional `issue`, rejects unknown fields, and explicitly rejects caller identity or provenance fields.
- A0-09: public `POST /v1/remediations` dispatches only the validated request and trusted tuple to the private workflow after all request and identity checks.

Cataloging FR-001 unchanged would make the authoritative catalog internally contradictory. Silently treating `user` and `tenant` as trusted-context fields would change the sentence’s stated payload contract and is therefore forbidden.

## Requested narrow authorization

Authorize changing only the FR-001 requirement sentence, while preserving ID `FR-001` and its absent severity (`null`), to:

> Accept a closed versioned remediation payload containing workspace and optional issue, and obtain user and tenant only from the gateway/PEP-owned verified identity context.

After authorization, the worker will update the canonical Markdown/catalog text together, add a semantic contradiction regression, rerun every A2-01 check, and continue without refreshing or bypassing SPEC-20 evidence.
