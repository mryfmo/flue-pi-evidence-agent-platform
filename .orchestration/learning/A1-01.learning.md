# A1-01 learning triage

## Candidate

Release evidence must hash all intended source bytes while excluding mutable validation outputs from the source set and binding those outputs separately. A single command manifest must be both executable by the producer and compared exactly by the consumer; matching display names or a count is insufficient.

Recursive entry sorting is not equivalent to sorting the flattened relative-path set; a directory and sibling file with the same prefix expose the difference. Repository identity parsers must anchor the complete transport and host, not search for a trusted-domain substring.

## Disposition

Candidate only. It is reflected in the A1-01 implementation and tests but is not promoted to a reusable project learn or skill by this worker. Orchestrator acceptance and future clean-tree release execution are required before promotion.

Stage 2A confirmed the generated inventory can be structurally valid while its source identity is still dirty. Manifest correctness and release-evidence acceptability are separate checkpoints: the former may pass before the orchestrator establishes the audited clean source state required by the latter.

Post-checkpoint line-ending normalization is a source-byte mutation even when semantics are unchanged. The release manifest must always be generated after such normalization; an otherwise valid pre-normalization manifest correctly fails its byte-digest binding.

An upstream merge that adds non-code release files changes the deterministic source tree just like code changes. The release inventory must be regenerated after merge and must bind binary bytes directly; filename presence alone is insufficient.
